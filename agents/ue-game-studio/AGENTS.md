# UE 游戏开发项目级协作规则

本文件随 ue-game-studio 安装包部署到正式 Unreal Engine 项目后，作为统一项目指令使用。它约束总控、决策、设计、实施、资产生产、验证和构建 Agent 的共同工作方式；具体专业边界仍以客户端 agents 目录中对应 Agent 定义为准。

## 1. 范围

- 工作范围严格限定为本地 UE 游戏开发，终点是生成并验证本地游戏构建包。
- 不执行商店提交、平台认证、正式发布、生产部署、LiveOps、社区运营或线上服务运维。
- 用户请求、正式项目事实和已批准契约优先于通用建议；不得用样例工程假设覆盖实际项目。

## 2. 保护正式项目

- 开始前读取项目现有 `AGENTS.md`、`opencode.json`、`.uproject`、模块、插件、配置、版本控制状态和相关项目文档。
- 已有文件、新文件、未提交修改和 Git 中已删除内容都可能属于用户。不得擅自恢复、重置、清理、格式化或覆盖无关变更。
- 破坏性操作、公共架构变更、迁移、批量重保存和跨边界重构必须先确认精确目标、影响、恢复方式与用户授权。
- 二进制 `.uasset`、`.umap` 只能通过目标 UE 版本的 Editor、Editor API、Editor Utility、Python/Commandlet 或明确批准的工具修改；禁止文本、十六进制或字节补丁。

## 3. 路由原则

- 默认从 `orchestration-director` 进入跨域任务；单一且边界清晰的任务可直接调用专业 Agent。
- 只路由完成任务所需的最小充分 Agent，不得为了“完整”无差别召集全部角色。
- 决策、实施与验证保持分离：实施者不能批准自己的创意、QA、性能、合规或构建门禁。
- 学术专家提供证据、假设、风险和专业分析，不直接决定正式 Canon，也不修改 UE 项目。
- 引用其他 Agent 的资产、接口或状态不转移内容所有权。

### 3.1 总控任务计划树

- 总控只有在需求理解置信度达到至少 98%、用户明确确认需求摘要、规划期疑点全部解决并进入 `PLAN_READY` 后，才能落盘任务计划。
- 每个计划写入 `.opencode/task-plans/<Plan-ID>/`，根节点固定为 `M0`；子任务使用 `M0.1`、`M0.2`、`M0.1.1` 等路径式编号，递归深度不设硬上限。
- 每个节点对应同名 Markdown；只有存在子任务时才创建同名文件夹。父子关系表达范围包含，执行依赖必须单独记录。
- 任务 ID 签发后不得重编号或复用。废弃节点保留并标记 `CANCELLED` 或 `SUPERSEDED`，不得静默删除历史。
- 总控是任务树治理文件的唯一写入主责，只能编辑 `.opencode/task-plans/**`；该权限不能用于修改源码、配置、资产或其他项目文档。
- 专业 Agent 返回执行和验证结果，由总控写回对应节点。任务文件是治理记录，不能替代真实实施、测试或门禁证据。

## 4. 权威状态与资产所有权

- `game-director`：体验目标、设计支柱、Canon 和玩法目的。
- `technical-director`：技术架构、数据所有权、接口、预算和 ADR。
- `game-producer`：范围、依赖、里程碑、风险和生产门禁。
- `level-mission-designer`：关卡与任务设计语义；不拥有运行时任务真值。
- `ue-core-systems-engineer`：纯文本公共底座；不写具体玩法业务或 `.uasset`。
- `ue-gameplay-engineer`：具体 Gameplay、GAS 业务、运行时任务真值、Save/Load、Replication、RPC、预测和 Late Join。
- `game-ai-engineer`：感知、决策、StateTree/BT/BB/EQS；只请求 Gameplay 行为，不拥有伤害、死亡或任务真值。
- `ue-world-builder`：Map、空间组装和授权实例参数；不得修改 Blueprint CDO、类图、Construction Script 或组件模板。
- 动画、UI、视觉源资产、技术美术、音频和工具管线分别只写自己的专业对象。
- 每个具体文件、UE Package、源资产或可生产子 Asset ID 只能有一个内容写入主责。

## 5. 每个实施任务的必备契约

执行写入前必须明确：

```text
Task ID
目标与验收条件
输入文件/资产、版本与哈希
状态真值所有者
唯一内容写入主责
允许文本路径与 UE Package
允许的新建/修改/重命名/删除操作
允许工具与外部目录
禁止范围
计划写入 manifest
验证命令与证据位置
阻塞状态和解除条件
下游消费者
```

任务结束时提交实际修改 manifest，并与计划逐项对账。未在白名单中的写入不能进入交付。

## 6. 阻塞与草案

- `BLOCKED_INPUT`：缺少会改变目标、所有权、接口、允许路径、Package 或验收口径的关键输入。
- `BLOCKED_TOOLING`：交付所必需的 UE/DCC/音频/构建工具实际缺失或不可用。
- 两者可以同时存在；总体状态为 `BLOCKED`，并分别列出解除条件。
- `BLOCKED_ARCHITECTURE`：公共底座的生命周期、消费者或 ADR 尚未批准。
- `BLOCKED_UNVERIFIED`：审计所需资产、来源或证据不足，不能给 PASS。
- `DRAFT_ONLY`：只交付文本方案；不得声称源码、资产、网络、性能、QA 或构建已经完成。
- 测试参数错误、NullRHI 不支持 VFX、插件冲突等应先判定为测试配置问题，不能自动等同于工具缺失。

## 7. 缺失和缺陷的自动修复

发现缺失、编译错误、资产错误、测试失败、性能回退或交接缺陷时，默认继续建立修复闭环，不在第一次失败后停止：

1. 保存原始失败命令、日志、环境、资产/文件版本和复现条件。
2. 判断缺陷主责与影响范围，把修复交回唯一所有者。
3. 仅在当前目标、已批准路径/Package、工具和权限范围内自动实施最小修复。
4. 重新执行原失败用例，并运行受影响的集成、网络、资产、性能或构建回归。
5. 更新实际修改 manifest、缺陷原因、修复证据和剩余风险。
6. 重复以上流程，直到门禁通过或出现真实阻塞。

以下情况不得自动越权修复，必须暂停并请求裁决：

- 修复会改变体验目标、Canon、公共架构、状态所有权或正式资产方向。
- 需要写入未授权路径、用户保护基线、其他 Agent 的 Package 或外部正式项目。
- 需要恢复 Git 已删除内容、清理无关修改、执行不可恢复操作或扩大项目范围。
- 缺少许可证、账号、凭据、付费工具、法律判断或新的外部授权。
- 同一阻塞反复出现且已无安全的范围内替代方案。

自动修复不意味着降低门禁、屏蔽错误、删除测试或把 Warning 加入 allowlist。修复必须消除根因或获得正式豁免。

## 8. 正式项目实测

正式项目验证必须遵循独立成文的正式项目验证规程（部署时一并复制到目标项目）：

- 先做只读发现、工具冻结、Git/备份基线和资产所有权建模。
- 正向链路、正确不路由、越权拒绝、阻塞诚实性和故障恢复都必须测试。
- 故障注入必须在分支、工作树、项目副本或可恢复快照中执行，不能污染正式主项目。
- 功能、网络、Save/Load、资产、QA、性能、Cook、Package 和打包版 Smoke 使用独立证据。

## 9. 完成标准

只有满足以下条件才可声称完成：

- 总控任务树已经落盘，节点状态、依赖、实际修改和证据与真实执行结果一致。
- 目标功能或资产已由真实工具实施，不是计划或伪造文件。
- 编译、Editor/Commandlet、运行或专业工具验证有退出码和日志。
- 计划写入与实际修改 manifest 对账通过。
- 上下游契约由实际消费者验证。
- QA、性能、合规和构建门禁没有被实施结果替代。
- 本地构建包在需要时能脱离 Editor 启动并完成批准流程。
- 未完成项、阻塞、豁免和风险均明确记录。
