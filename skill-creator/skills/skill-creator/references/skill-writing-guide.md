# 技能写作规律（TDD 化 + 表述匹配失败类型）

> 反哺来源：上游 obra/superpowers 仓库的「writing-skills」技能（社区成熟方法论，含措辞对照实证）+ Anthropic 官方技能写作最佳实践。2026-09-03 对比本地 skill-creator 后吸收（记录见 `evolutions/2026-09-03-adopt-superpowers-writing-skills.md`）。
> 本文件补充 SKILL.md 阶段 4/6/7 与 `quality-bar.md` 的**写作规律**细节；触发量化工具见 `scripts/run_eval.py` / `run_loop.py` / `aggregate_benchmark.py`，此处不再重复。

## 1. 铁律：无「失败先例」不写技能（RED-GREEN-REFACTOR）

技能写作 = **对过程文档做测试驱动开发**：

| TDD | 技能写作 |
|---|---|
| 先写测试（RED） | 无技能状态下跑真实压力场景 → **记录 agent 的失败与借口（verbatim）** |
| 写生产代码（GREEN） | 写**只针对这些具体失败**的最小 SKILL.md |
| 重构（REFACTOR） | 重测；发现新借口 → 补显式反制 → 再测，直到无法绕开 |

**Iron Law：先看 agent 无技能时的基线失败，才知道技能该教什么。**
- 没看失败就写 = 盲写；写完整再测 = 亡羊补牢。
- 适用于**新技能与对既有技能的每次编辑**：新增章节也要先问「基线会怎么失败」。

本地已具备的量化基建：阶段 6 的「有/无技能基线对比」+ `aggregate_benchmark.py` 的 delta 判定——**纪律缺口在顺序**：基线必须发生在写作之前，且失败记录要 verbatim 存档。

## 2. 表述形式匹配失败类型（核心实证规律）

动笔前先给基线失败**分类**，再选表述形式。选错形式会适得其反：

| 基线失败 | 正确形式 | 错误形式 |
|---|---|---|
| 压力下**违反规则**（明知故犯） | 禁止 + 借口表 + 红旗清单（见 §3） | 软性建议（"prefer…/consider…"） |
| 照做但**输出形状错**（结构不对、藏结论、复述规格） | **正面配方/契约**：描述输出**是什么**——分几部分、什么顺序 | 禁止清单（"don't X"） |
| 产出物**漏必需元素** | 结构强制：在模板里留 **REQUIRED 槽位** | 模板旁的空泛提醒 |
| 行为应随**条件**变化 | 条件绑定**可观察谓词**（"若 brief 存在则引用它"） | 无条件规则 + 豁免条款 |

**实证反直觉点：禁止类措辞对「形状错」问题会反噬。** 在「让输出自包含」的对照测试里，禁止组产出的冗余内容比基线组还多、甚至比无指导组更差——代理会和 "don't X" 谈判。配方没有可谈判空间：输出符合形状或不符合。

**选型后的两条硬规则：**
- **不加 nuance 子句**：「don't X unless…」会重新打开谈判——给一条获胜配方追加单个 nuance 子句就能把它从稳定打成嘈杂。真实例外应表达为**基于可观察谓词的条件**。
- **豁免子句框不住行为**：「此限制不适用于代码块」照样压制代码块。某部分需豁免时，重排结构让规则碰不到它。

## 3. Bulletproofing：防「合理化（rationalization）」

仅适用于**纪律型失败**（明知规则、压力下想绕开）。形状错/漏元素禁用此套（用 §2 对应形式）。

- **封死每个漏洞**：不只说规则，显式列工作区变体——「改后补测？删掉重来」「别留作 reference」「别边测边改」。
- **字即神**：`违规则之字面即违规则之精神`——一句封掉整类「我在守精神」的诡辩。
- **借口表（Rationalization Table）**：把基线测试里 agent 的真实借口逐条入库：

  | 借口 | 现实 |
  |---|---|
  | "太简单不用测" | 简单最易错，测只要 30 秒 |
  | "先写完再测也一样" | 事后测回答「它做什么」，事前测回答「它该做什么」 |

- **红旗清单**：给自查的低成本触发器——「代码先于测试」「我已手动验证过」「这是精神不是仪式」。每条尾注「**出现即：删掉重来**」。
- **把「即将违规的症状」写进 description**，让触发即预警。

## 4. 措辞微测：先于全量压力场景（省钱且更强）

全量压力场景是终局闸门，但每轮贵且慢。先用**措辞微测**筛写法：

1. 每次调用一个 fresh-context 样本（裸 API 或单发 subagent）；system prompt = 指导将生存的真实上下文（整份技能/模板），user 消息 = 诱发该失败的任务。
2. **必带 no-guidance 对照组**——对照组不失败 = 没有要修的东西，停止，别写指导。
3. **每个变体 ≥5 次**——单样本会骗人。
4. **人工逐条读命中**——模板回声与引述反例会冒充命中，自动计数会同时高估成败。
5. **方差即指标**：指导生效时各次收敛同形；5 次 5 种解释 = 措辞不具约束力，先紧形式再加字。

微测只验证措辞，纪律型技能仍需压力场景兜底。

## 5. 技能类型与取舍（先筛后写）

三种类型，测试重点不同：
- **Technique（技法）**：有步骤可循。测：能否应用于新场景 / 边界 / 信息缺口。
- **Pattern（思维模型）**：看问题的方式。测：何时该用 / 何时不该用 / 反例识别。
- **Reference（参考）**：API/语法/工具文档。测：能否检索到 / 用对 / 常见用例覆盖。

**取舍闸门：能用 regex/校验/工具自动强制的机械约束，不要做成技能**——自动化它，文档只留给判断类决策。「创建当」：技法不直观、跨项目复用、模式普适、他人受益；「不创建」：一次性方案、文档齐全的标准实践、项目内约定（放 instructions 文件）。

## 6. 触发面（description）与命名

**description = 何时用，不是做什么。** 实证：description 总结工作流时，agent 会照 description 走捷径、跳过正文（曾出现「技能流程图规定两阶段审查，agent 只做了一次」）。细则：
- 以**触发场景/症状**开头（Use when / 何时）；可保留**一句能力定位**（供技能目录渲染「用途」列），但**绝不写执行步骤/流程阶段摘要**。
- 写**问题**（竞态、不一致行为）而非语言症状（setTimeout）；技术特定技能才显式写技术。
- 第三人称、关键词覆盖（错误串/症状/同义词/工具名）。

**硬约束（description 是唯一无条件加载的触发面）**：
- `description` 是客户端在触发前**唯一始终加载**的字段——必须**自足**：覆盖全部会触发它的用户说法，不指望正文兜底。写正文前，先拿 description 当唯一门面试触发查询，问「只看这句，该技能会被调吗」。
- ≤1024 字符、**单行**、**不含 `<`/`>` 占位符**（`<技能名>`、`<path>` 会让触发匹配失真）。validate_skills 在 strict 下可报此 advisory。
- 正文的「何时使用此技能」章节是**触发后**的范围确认，不承担触发职责——两者职责不同，别把正文当 description 的展开版互相抄。

**触发失败先归因再改**：假阴性（漏触发词/说法）→ 补触发面；假阳性（过度匹配/兜底 catchall）→ 收窄到具体场景，别堆穷举清单；run_error（工具/依赖问题）→ 与描述无关，别乱改 description。

**命名**：动作优先（`creating-skills` 而非 `skill-creation`）、动名词适合流程；仅字母数字与连字符。
**注意反模式：不用 `@` 语法引用其他技能**——`@` 会 force-load、烧上下文。跨技能引用用显式要求标记：`**REQUIRED BACKGROUND:** 必须先理解 xxx-skill` 或纯技能名 + 一句话何时用。

## 7. Token 预算（按加载频率）

- 常驻/高频加载技能：正文尽量 <200 词总量；getting-started 类 <150 词。
- 通用技能：<500 词仍须克制；细节进 references/ 或工具 --help。
- 用交叉引用替代重复；每条示例只保留一个优秀示例（禁止多语言稀释）。
