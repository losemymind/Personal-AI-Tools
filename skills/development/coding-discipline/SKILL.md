# 编码行为纪律（Coding Discipline）

## 概述

四条减少 LLM 常见编码错误的行事准则：想清楚再动手、保持简洁、只改动必要的部分、以可验证目标驱动。它们针对四类高频问题——替用户默默做假设、把简单问题过度工程化、顺手改动无关代码、用模糊标准代替可验证目标。本技能不教具体语言或框架，只约束编码过程中的判断与改动范围。

## 何时使用此技能

- 用户要求编写新功能、修改现有代码、重构或调试（任何非 trivial 的编码任务）
- 你即将替用户做假设（文件位置、数据字段、范围、格式）却未确认时
- 你打算引入抽象、配置项、错误处理或「以后可能用得上」的灵活性时
- 除用户请求的行之外，你还想改动相邻代码、注释或格式时
- 用户给出模糊目标（「修好它」「让它更快」「优化一下」）时

## 工作原理

### 准则 1：想清楚再动手

不要替用户默默选择一种解释。先把不确定性和权衡摆出来：

- 列出你正在做的假设，逐条标注「已验证 / 推测 / 需要用户确认」。
- 发现歧义时，列出所有合理解读及各自成本，而不是挑一个就开工。
- 存在更简单的做法时，主动指出来。
- 卡住时，说清哪里不清楚并提问，不要猜。

反例：用户说「加一个导出用户数据的功能」，你直接假设导出全部用户、写死文件名与字段就开始写。正例：先确认范围（全部还是筛选）、形式（下载 / 后台任务 / API）、字段（是否含敏感字段），再给一个最小方案。

### 准则 2：保持简洁

只写解决当前问题的最小代码，不做推测性设计：

- 不为一次性使用写抽象（策略模式、工厂、基类）。
- 不实现用户没要求的「灵活性 / 可配置性 / 未来扩展」。
- 不为不可能发生的场景写错误处理。
- 如果 200 行能写成 50 行，重写。

判断标准：一个资深工程师会不会说这过度复杂？会，就精简。

反例：为「按百分比算折扣」这一个需求，定义 `DiscountStrategy` 抽象基类、`PercentageDiscount`、`FixedDiscount` 和 `DiscountConfig`。正例：

```python
def calculate_discount(amount, percent):
    """按百分比计算折扣金额。percent 取值 0-100。"""
    return amount * (percent / 100)
```

只有当「多种折扣类型」这个需求真的出现时，才引入抽象。

### 准则 3：只改动必要的部分

让每一行改动都能追溯到用户的请求：

- 不要「顺便改进」相邻的代码、注释或格式。
- 不要重构没有坏的代码。
- 与既有风格保持一致——即使你会写得不同。
- 发现与任务无关的死代码，指出来，但不要删。
- 你的改动产生的孤立 import / 变量 / 函数，清理掉；既有的死代码，除非用户要求，否则保留。

反例：修「空 email 崩溃」的 bug 时，顺手换了引号风格、加了类型注解、加了用户名字段校验。正例：只改处理空 email 的那几行，其余原样保留。

### 准则 4：以可验证目标驱动

把命令式任务转成带验证点的目标，再循环执行直到验证通过：

| 不要这样说 | 改写成 |
|---|---|
| 「加个校验」 | 「先写非法输入的测试，再让它通过」 |
| 「修这个 bug」 | 「先写一个能复现它的测试，再让它通过」 |
| 「重构 X」 | 「确保重构前后测试都通过」 |

多步任务先给出简短计划，每步附一个可观测的验证点：

```text
计划：
1. [步骤] → 验证：[可观测检查]
2. [步骤] → 验证：[可观测检查]
```

强成功标准（有数字或布尔结果）让代理能独立循环；弱标准（「让它能用」）需要反复澄清。

## 示例

### 示例 1：模糊目标转成可验证计划

用户说：「给 API 加限流。」

不要一次性实现 Redis + 多策略 + 配置系统 + 监控（300 行、无验证点）。改成：

```text
限流实施计划：
1. 加基础内存限流（单端点）
   验证：测试发 11 次请求 → 前 10 次成功，其余返回 429
2. 提取为中间件（应用到所有端点）
   验证：限流对 /users 与 /posts 均生效
从第 1 步开始？
```

### 示例 2：先复现再修 bug

用户说：「有重复分数时排序结果不稳定。」

不要直接改排序逻辑。先写一个复现测试，确认它在修复前失败（顺序不确定）；再改代码；最后确认该测试稳定通过，且其他排序测试没有回归。

## 最佳实践

- ✅ 动手前用一两句话复述你理解的请求，让误解尽早暴露。
- ✅ 改动范围以「用户请求」为界，越界前先说明并征求同意。
- ✅ 把观察到的无关问题记成备注，而不是直接动手。
- ❌ 不要引入用户没要求的抽象层、配置项或「以后可能有用」的代码。
- ❌ 不要用顺手的重构扩大 diff。

## 相关技能

- `code-review-skill` — 需要结构化代码审查（架构 / 性能 / 安全维度）时使用；本技能约束编码行为，不替代审查。

## 常见问题

**Q：任务很小，也需要走这四条吗？**
A：不需要。拼写修正、明确的一行改动、格式调整直接做即可。这套准则的价值在于减少非 trivial 任务上的代价。

**Q：保持简洁会不会写出以后要重写的代码？**
A：会写出「当下够用」的代码，这正是目的。需求真正出现时再重构，比提前猜测需求更省事。

## 限制和注意事项

- 只约束编码行为与改动范围，不提供具体语言、框架或 API 知识。
- 不适用于 trivial 任务（一行修 bug、拼写修正、格式改动），此时全量准则反而降低效率。
- 偏向谨慎而非速度；原型探索等追求快速迭代的场景可自行放松约束。
- 需与项目自身的 lint 规则、编码规范配合使用。
- 不替代人工审核：涉及推送生产、删除数据、修改配置等外部动作时仍需用户确认。
